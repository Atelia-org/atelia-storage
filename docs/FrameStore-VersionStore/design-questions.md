# 下一轮设计难题：分配、提交与发布

日期：2026-10-04。状态：**Informative / Derived；问题汇总，不是新增实施阶段或规范输入**。
输入为本轮会话和 S0–S6 的 Draft 合同。本轮仅修订文档；S1 与 RBF1 参考隔离的已有 Accepted 资格保留原身份，不构成新模型已实施的证据。

## 已形成的方向

FrameStore 普通合同为不透明分配和随机读取；文件顺序只服务底层恢复。需要确定追加顺序的消费者显式使用 FrameLog。VersionStore 在 data 中保存不可变提交，在私有 control 日志中发布 ref/name；提交 parent 与 ref previous revision 分开。
首版技术默认为单 driver、单 active 后端、批次 BeginNext、单 parent 提交、全控制回放和同步全 owner barrier。它们仍是候选，不能因写入 Draft 就当作额外用户决策或实现承诺。

## 优先讨论的问题

### D1：分配器和 FrameLog 的公共边界如何落地？

**涉及阶段：** [S2](02-framestore-core.md) 的 S2-Q1/Q4，随后 S4-Q3。

**难点：** 普通分配不承诺顺序，控制回放却必须取得真实主链与唯一后缀。若只是给 FrameStore 的任意 inventory 排序，就会把数据布局变成发布权威。若为 FrameLog 完整复制存储实现，又会产生两套轮转/恢复/耐久逻辑。

**当前候选：** 同一生产项目内两种窄 facade，共用后端；格式门持久区分 Allocator/Log；日志不暴露可绕过顺序的写入口。独立 owner/目录和身份，不提供通用多流平台。

**待定：** 采用具体类还是能力接口；factory/用途字段/版本及拒绝规则；cursor 的持久编码与校验；后端资源归属。S2 需先独立形成合同，S4 不能绕过它直接持有裸 RBF。

**收敛标准：** 不认识 VersionStore 的最小消费者也能证明有序日志与 allocator 都独立可用，且一个 owner 无法经另一个 facade 绕过 bookkeeping。

### D2：持久分配器需要多强的构建自由？

**涉及阶段：** [S2](02-framestore-core.md) 的 S2-Q4/Q5；[S3](03-framestore-batches-and-durability.md) 的 S3-Q1/Q2。

**难点：** 随机读取、不透明文件选择、任意填充次序和多个活跃 Builder 是不同能力。当前 RBF 单文件只接受一个 Builder，活跃期间门面读取受限。将这些一并许诺为“像内存堆”，会隐含增加缓冲、调度或多个 active 文件的成本。

**当前候选：** 先拿到全部地址，通过 BeginNext 串行填充；不复制整批 payload。owner 在活跃 Builder 期间拒绝读取/扫描，已物化数据继续可用。应用可提前编码循环引用，但不能跳过当前项。

**待定：** 真实状态构建是否需要先填 B 后填 A，或边写新帧边按地址读取旧帧；若需要，选择有预算的暂存、独立历史 reader 或不同文件调度，并明确取消、内存和 flush 成本。不能让消费者自行指定物理文件来绕开限制。

**收敛标准：** 用一次完整构建轨迹证明候选满足消费者；如果限制不足，先改 S2/S3，再推进 S4，不以同文件循环示例替代任意完成次序。

### D3：重开后如何确认提交、parent 和未发布帧的来源？

**涉及阶段：** S2-Q1/Q4、S3-Q4；[S4](04-versionstore-publication.md) 的 S4-Q2/Q6。

**难点：** CRC 正确、地址合法、位于真实帧集合、来自一次完成创建以及业务闭包合法，是不同资格。仅 ReadCommit 解码成功不足以证明原始创建来源；仅保留进程内 handle 又不能支持冷重开、旧提交选择和完整 orphan 的显式采用。

**当前候选：** 正常 CreateCommit 只接受已完成 parent；控制回放不 eager 读取全部提交。Prepare 定点 ReadCommit，应用负责 opaque 状态闭包，完整 orphan 必须重新确认，禁止沿用取消计划的来源。

**待定：** 采用何种完成来源见证/窄 handle；已接受发布是否足以恢复旧提交资格；未发布提交如何通过显式 inventory/成员验证取得资格；CreateCommit 检查一个 parent 还是祖先链，成本如何界定；提交 codec 如何与普通应用帧区分。

**收敛标准：** 明确覆盖冷重开后的合法旧提交、未发布完整提交、嵌套伪 ticket、取消地址复用及坏 parent。正常 writer 的无环证明不依赖物理大小比较；无法验证来源的操作明确拒绝或进入显式验证路径，不静默假定成功。

### D4：提交创建结果未知时，需要怎样的外部追踪？

**涉及阶段：** S4-Q4/Q6。

**难点：** 根发布已有输出前 token 和 Unknown 查询，但 CreateCommit 是另一次 data 追加。异常可能留下完整提交，也可能被截断；已知数值地址后来可能复用，因此无法直接把它当作精确尝试身份。

**当前候选：** CreateCommit 不改变 ref；异常后停止相关实例并重开，未知提交不作为成功返回对象、不自动 retry。可以放弃孤立提交，重新构建一份并明确发布。发布操作仍以现有 token 查询结果。

**待定：** 首版是否只需要“放弃未知未发布提交”的流程，还是要单独恢复某次提交创建结果；若需要精确追踪，再设计尝试身份/查询，不直接借用 control RefRevision，也不为所有普通数据帧增加 pending 日志。

**收敛标准：** 提交未知与发布未知分开；恢复后应用不会把同地址的另一帧当作原提交，也不会仅因找到完整提交而安装新状态。

## 其余定稿项与条件扩展

地址 wire/非法值、格式门/locator、轮转阈值及平台原子替换、资源释放、名称规则和分页预算仍在各阶段 Ready 表中定稿；它们不能被本轮概念修订自动跳过。
FrameAddress 不透明不等于支持搬迁。首版可用直接定位编码，先取得存续期间地址稳定资格；GC/compaction、逻辑 ID 映射、多个 active 文件、多个 data owner、跨实例 CAS 和更强断电模型在有需求时单独设计。
多 parent/merge、children 反向索引、内容寻址、archive/provenance 和 snapshot 不作为本轮核心前置。tag/branch 统一指向提交；如将来需要“给任意状态帧命名”，须显式扩展语义，不把它混入当前 tag 合同。
